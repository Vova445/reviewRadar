===== docs\production-architecture.md =====
1: # ReviewRadar production architecture
3: ## Runtime boundaries
5: `Next.js UI → HTTPS API/BFF → PostgreSQL + Redis-compatible queue → workers`
7: The browser never calls the AI provider, Google Business Profile, PostgreSQL, or Redis directly. Next.js Route Handlers authenticate the user, resolve workspace membership, validate request input, and call the backend API. The API owns authorization and transactions. Workers own Google synchronization, AI analysis, anomaly detection, alerts, reports, and retention cleanup.
9: For the Sites-hosted frontend, PostgreSQL and Redis must stay behind the external HTTPS API because the hosting runtime does not support raw TCP database connections. The former D1 binding is disabled. `db/schema.ts` is retained only as prototype history; `db/postgres/001_initial.sql` is the production schema source.
11: ## Queue pipeline
14: 2. API enqueues `review.analyze` with review/workspace/location IDs and an idempotency key.
15: 3. AI worker loads temporary review content server-side.
21: Dead-letter queues retain identifiers and sanitized errors, not full Google review content. Every consumer is idempotent and retry-safe.
25: PostgreSQL performs deterministic aggregation over structured `review_topics`. It computes counts and growth between equal windows. Only anomalous clusters above configured support/confidence thresholds are sent to AI for a short explanation and recommended actions. The model is never asked to repeatedly analyze the entire review history.
29: OAuth tokens are envelope-encrypted before persistence; ciphertext and encryption key ID are stored, never plaintext refresh tokens. Data keys and provider secrets live in a managed secrets/KMS system. Logs must redact authorization headers, tokens, review text, AI prompts, and database URLs.

===== docs\review-analysis-and-retention.md =====
1: # Review analysis and Google Content retention
5: The database separates provider metadata, temporary source content, and ReviewRadar-derived analysis.
7: - `reviews`: workspace/location ownership, source identifiers, rating, provider timestamps, fetch time, and retention deadline.
8: - `review_source_content`: temporary Google-sourced author, comment, reply, language, and content hash. `purge_after` is set from the policy-aware retention configuration and never later than the currently permitted window.
13: The production implementation must re-check the current Google Business Profile policies and contractual terms before launch. A scheduled retention job deletes expired `review_source_content`; refresh-on-demand must not silently extend retention beyond what the current policy permits. Deletion must also cover logs, queues, debug payloads, exports, backups, and AI-provider request retention.
21: System topics provide stable reporting dimensions for a business vertical. AI-discovered topics are created only after normalization, confidence checks, and similarity matching to avoid duplicates such as `wait time`, `waiting`, and `long queue`. A human can later merge or promote discovered topics without rewriting historical reviews.
